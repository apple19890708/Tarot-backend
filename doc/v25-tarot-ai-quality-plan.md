# v25　塔羅 AI 解讀的品質與穩定度

建立日期：2026-11-19
狀態：階段 1～5 已實作（2026-11-19），評估跑過一次；待部署後線上累積檢查結果與回饋

## 一、目標

讓塔羅 AI 解讀**更貼近問題、每次品質更一致**，而且做法不是只靠加長提示詞。

起因：2026-11-19 使用者問「只靠 prompt 好像沒辦法讓品質穩定」。目前狀況：

- 系統提示約四五千 token。是非題、時間題、關係牌陣、宮廷牌、股市版的規則全部放在同一份，規則越多每一條越容易被忽略，彼此也會互相稀釋。
- 改提示詞或換模型之後，沒有固定的題目可以比較，只能等使用者看到問題再修。v23 的「黃仁勳兩次都答不會」、「11 月答今年夏末秋初」都是上線後才發現的。
- 寫出來的內容沒有任何檢查，例如漏了段落、是非題第一句沒回答、時間題沒給日期，都不會被記錄。

方向分四層，照效益與成本排序：

1. 程式能算的先算好，AI 只負責解釋（v23 的規則 12、13 已經這樣做，這一版延伸）。
2. 依問題類型組提示詞，只給用得到的規則與範例。
3. 寫完用程式檢查，不合格的記下來。
4. 一組固定的評估題目，加上使用者回饋，讓每次改動都有依據。

### 不做的事

- **不換模型、不調高預設的推理強度**。維持 Sonnet 5.5、medium。前面幾層沒做好之前，換更強的模型提升有限，費用卻是倍數增加。只有階段 5 依牌數調整推理強度。
- 不做「寫完再讓 AI 自己檢查、自己重寫」的第二次呼叫。費用加倍，而且要等更久；檢查用程式做（階段 2）。
- 檢查到不合格**不自動重寫**，只記錄。等累積資料、知道哪些規則常被違反，再決定要改提示詞還是補寫。
- 不改股市版（`MARKET_INSTRUCTIONS`）的結構與個股、財經新聞的 AI 分析。這一版只處理塔羅解讀與追問；股市版只跟著拆段落，內容不動。
- 不在前端改寫或組 AI 的文字；前端只增加回饋按鈕（階段 4）。
- 評估不在 CI 或部署時自動跑；每次跑都要花 OpenRouter 的錢，一律由使用者同意後手動執行。

## 二、規格

### 階段 1：問題分類與分段的提示詞

**1-1. 問題類型（程式判斷，不呼叫 AI）**

新增 `src/services/rules/questionType.js`，回傳 `{ kinds: [...], topic }`：

- `kinds`（可以同時有多個）：
  - `yesNo`：沿用 `detectYesNo`。
  - `timing`：沿用 `isTimingQuestion`。
  - `choice`：在選項之間選，例如「A 還是 B」「選哪一個」「二選一」。「該不該」「要不要」歸是非題，不算選擇題。「還是」前面是人稱或副詞時是「仍然」（「他還是會回來嗎」），不算；「哪個月」「哪個時候」是時間題。
  - `open`：上面都不是。
- `topic`：**沿用規則 7 已決定的領域**（`quant.domain`：工作、財務、感情、人際、股市、學業與決策、綜合），不另寫一套關鍵字。
- `othersInvolved`：沿用宮廷牌用的 `hasOthersInQuestion`。
- 牌陣另外看：關係牌陣（`relationship`）、張數 ≥ 5、有沒有追問。

分類結果放進 `analysis.questionType`，也交給 AI。舊紀錄沒有這個欄位時，讀取時重新算。

**1-2. 系統提示拆成「共用」加「依類型」的段落**

把 `SYSTEM_PROMPT` 拆成：

| 段落 | 內容 | 什麼時候放 |
|---|---|---|
| 共用 | 角色、語氣、資料怎麼用、結構、格式、禁止事項 | 一律 |
| 是非題 | 第一句回答、參考是非判斷、兩邊拉扯的寫法 | `yesNo` |
| 時間題 | 一定給日期、從今天往後算、逆位延遲 | `timing` |
| 選擇題 | 各選項分開比較、最後明講建議哪一個 | `choice` |
| 關係牌陣 | 雙方對照、宮廷牌優先讀成人 | 關係牌陣，或 `topic` 是感情或人際 |
| 範例 | 共用段落裡原本那篇；是非、時間段落各附一句「開場示範」 | 一律 |

- 組合的函式寫在 `buildSystemPrompt({ questionType, spread, market })`，測試直接檢查組出來的文字，不必呼叫 AI。
- **提示詞快取**：快取是照開頭相同的部分算的。共用段落放最前面並加快取標記，依類型的段落放在後面。這樣不同類型的問題仍然共用前面那一大段的快取。
- 追問的 `FOLLOW_UP_PROMPT` 照同樣方式拆。
- 量測（2026-11-19）：原本的系統提示 7176 字。一般問題 6129 字（少 15%）；是非題 6846 字（少 5%）；時間題 6629 字（少 8%）；選擇題、關係問題因為加了新的段落，和原本差不多。**沒達到原訂少三成的目標**：共用段落主要是語氣、結構與範例，這些每一題都要用。省下的主要是快取：評估中第五題之後，每一題都有 6642 token 命中快取，不同類型的問題也共用同一段。

**1-3. 程式再多算幾項交給 AI**

- **主牌**：結果或未來位置的牌（沒有時用最後一張），加上焦點牌，寫成「這次最關鍵的牌」放在組合分析開頭（`analysis.keyCards`、`questionType.pickKeyCards`）。
- **問題類型**：寫成「問題類型：是非題、問時間」放在組合分析開頭。
- **選擇題**：不另外對應位置；二選一牌陣本來就有「甲／乙」的位置，一般牌陣由選擇題段落要求 AI 依時間位置與結果牌推。

### 階段 2：寫完用程式檢查

新增 `src/services/narrationCheck.js`：`checkNarration(text, { questionType, spread, market, followUp })`，回傳不合格的項目代碼陣列。檢查項目：

| 代碼 | 檢查什麼 |
|---|---|
| `missing-section` | 結構要求的 `##` 標題有沒有缺，順序對不對 |
| `yesno-first-line` | 是非題：開場第一句有沒有「會」「不會」「傾向」這類回答 |
| `timing-no-date` | 時間題：有沒有出現年份或月份 |
| `timing-past-date` | 時間題：講到的月份是不是已經過去（例如 11 月說「今年夏天」） |
| `leaked-score` | 有沒有寫出分數、百分比（提示詞禁止） |
| `removed-section` | 有沒有出現已經拿掉的段落（例如「你可以問自己」） |
| `too-short` / `too-long` | 字數明顯偏離要求 |
| `truncated` | 結尾停在句子中間（被 `max_tokens` 截斷或串流中斷） |

- 還有一項 `foreign-script`：夾雜西里爾字母、日文假名（提示詞要求只用繁體中文）。
- 存進紀錄時由 Reading 的 `pre('validate')` 執行，所有存解讀的路徑（保存、補存、後端存回、追問）都會經過，前端不用送。結果存在 `narration.checks`（代碼陣列）與 `narration.promptVersion`（常數 `PROMPT_VERSION`，在 `narrationCheck.js`，每次改提示詞加 1；v25 為 2）。**只改回饋時不重算**，文字換了才重算。追問的延伸回答同樣存在 `followUpNarration`。
- 不擋、不重寫，只記錄。使用者看到的內容不受影響。
- 管理頁先不做統計畫面；統計用唯讀腳本 `node scripts/narrationQualityStats.js`（依 `promptVersion` 分組，只做彙總，不讀出內容與問題）。
- 測試：每個代碼都要有合格與不合格的真實段落各一個。

### 階段 3：固定的評估題目

- 新增 `eval/cases.json`：20～30 組「問題＋牌陣＋抽到的牌」，涵蓋：
  - 是非題（含 v23 的兩組 NVIDIA 牌）
  - 時間題
  - 選擇題
  - 感情與關係牌陣
  - 工作、財務
  - 開放式問題
  - 有追問的
  - 股市問題（只看塔羅那一半）

  每組可附「預期」，例如是非題應該答「傾向會」、時間題的日期要落在哪個範圍。
- 題目來源：使用者提供，或從使用者自己的紀錄挑選後匿名化（問題改寫成不含個人資料）。**不讀其他會員的紀錄**。
- 題目放在 `eval/cases.json`（2026-11-19 版：22 題解讀＋3 題追問）。
- 新增腳本 `scripts/eval-narration.js`（牌庫從資料庫的 cards 讀，只讀牌）：
  - 預設只做「乾跑」：組出每一題要送的提示詞、估算 token 數與費用，**不呼叫 AI**。
  - 加 `--run` 才真的呼叫 OpenRouter。執行前印出題數與預估費用，等使用者確認。
  - 結果寫到 `eval/results/<日期>-<promptVersion>.json`，這個資料夾不進 git。
  - 每題自動跑階段 2 的檢查，並對照「預期」；最後印出各代碼不合格的題數，以及和上一次結果的差異。
  - `--recheck=<結果檔>`：改了檢查規則後，用存好的結果重跑檢查，不呼叫 AI。
- 人工看：每次挑 3～5 篇讀過，在結果檔裡寫備註。
- 使用時機：改提示詞、換模型、改推理強度之前與之後各跑一次。

### 階段 4：使用者回饋

- 前端：AI 解讀與追問回答的最下面放「有幫助／沒幫助」兩個按鈕；按「沒幫助」時可以選原因（沒回答到問題、太籠統、時間不對、太長、其他）。再按一次同一個是取消。只有已經是紀錄（有 id）時才顯示；占卜頁 AI 解讀寫完會自動保存，所以登入後就會出現（`NarrationFeedback.vue`）。
- 後端：`PUT /api/readings/:id/narration-feedback`，body `{ target: 'narration' | 'followUp', value: 'up' | 'down' | null, reason? }`，只能改自己的紀錄；還沒有解讀時回 409。存在 `narration.feedback`：`{ value, reason, at }`，追問回答存在 `followUpNarration.feedback`；重新產生後是新的一篇，回饋跟著清掉。單筆回顧會回傳 `feedback`。
- 新欄位都是可選的；舊前端不會送，舊紀錄沒有這個欄位。
- 用途：搭配 `promptVersion` 與 `checks` 統計；被評「沒幫助」的題目，經使用者同意後補進階段 3 的評估題目。

### 階段 5（可選）：依牌數調整推理強度

- 牌數 ≥ 6（關係牌陣、凱爾特十字），或有兩次以上的追問時，推理強度用 `high`；其他維持環境變數的設定。
- 新環境變數 `OPENROUTER_REASONING_EFFORT_LARGE`（沒設定就不調整）。程式已做好，**Cloud Run 沒有設定**，等於關閉。
- 要先用階段 3 比較 medium 和 high 的差別，確定有差才開。這次的評估只跑了 medium（使用者只同意跑一次）。

## 三、階段與進度

| 階段 | 內容 | 要不要花 AI 費用 | 狀態 |
|---|---|---|---|
| 1 | 問題分類、提示詞分段、多算主牌 | 不用 | 完成 2026-11-19 |
| 2 | 寫完的程式檢查、記錄 `checks` 與 `promptVersion` | 不用 | 完成 2026-11-19 |
| 3 | 評估題目與腳本 | 乾跑不用；`--run` 要，每次先問 | 完成 2026-11-19，跑過一次（見第六節） |
| 4 | 使用者回饋按鈕與 API | 不用 | 完成 2026-11-19 |
| 5 | 大牌陣用 high（可選） | 比較時要 | 程式完成，未啟用（沒比較過） |

建議順序：**2 → 1 → 3 → 4 → 5**。先做檢查，才量得出提示詞分段前後的差別。

- 2026-11-19 使用者用自訂位置（主觀感受×2、客觀事實×3、塔羅建議×1）問「對一個人不舒服是不是刻板印象」，並指出聖杯王牌在「客觀事實」應讀成提問者的直覺。改三處：

  - 規則引擎：自訂位置**名稱完全相同**才算一組（使用者決定，「客觀事實 1」「客觀事實 2」不算），牌對改成組內相鄰「同組」（新的關係型態 `group`）＋組與組之間一對「對照」；交給 AI 的 `<spread>` 多一行「位置分組」。沒有同名時行為不變。
