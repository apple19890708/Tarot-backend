# v23　塔羅是非題判斷與抽牌追問

建立日期：2026-11-13
狀態：已實作，待線上確認（AI 產出的內容需要實際產生一篇才能看）

## 一、目標

1. **是非題要答得出會或不會，而且和一般塔羅師的讀法一致。**
   起因：2026-11-12 使用者問了兩次「Nvidia 黃仁勳會因為這次風波下台嗎」，一般塔羅師會讀成會，AI 兩次都答不會。
   - 第一組：錢幣皇后正、寶劍五逆、聖杯七正
   - 第二組：權杖十逆、聖杯七正、聖杯國王逆
2. **抽牌追問**：占卜完可以針對同一件事再問、再抽 1～3 張補充牌，最多三次；AI 把原牌陣和所有補充牌放在一起回答，結果接在原本的 AI 解讀下面。

### 不做的事

- 不拿真實世界的結果驗證命中率（塔羅的答案無法這樣驗證）。這裡能量測的是「和塔羅傳統讀法一致」的程度，用典型牌面當對照組。
- 不改規則 11 的指向分數（順不順）。它照舊顯示，只是不再被當成是非題的答案。
- 不處理否定問句（「他不會被換掉吧」）與二選一（「會離開還是留下」）：前者照肯定問句算，後者不當是非題。
- 補充牌不併入原牌陣的組合分析（牌對、數字階段、指向都不重算），只在追問的延伸回答裡一起看。
- 追問的延伸回答不查市場資料（股市諮詢的追問只談牌）。
- 追問不做「輸入已抽到的牌」；自己抽牌沒有飛牌動畫（牌直接出現在補充牌格子）。

## 二、規格

### 2.1 診斷：為什麼會答不會

| 原因 | 說明 |
|---|---|
| 系統沒有是非題的概念 | 規則 11 只算「順利／不順」，提示詞要求 AI 的結論與它一致。問「會不會被換掉」時「偏順利」沒有定義，AI 讀成「現狀順利，所以不會」 |
| 逆位不翻向 | 逆位只把極性打成 0.45 倍，正負不變。78 張裡 53 張是正分，逆位後沒有一張變負。皇帝逆（權位不保）仍是 +0.27 |
| 分數整體偏正 | 隨機抽牌 2 萬次的平均 DI 是 +14～+15；三張牌陣「偏不順以下」只有 7.6%，七張牌陣 1.6% |
| 變動牌的極性方向和是非題相反 | 命運之輪 +0.5、審判 +0.5、世界 +0.9、死神 −0.2。問「會不會換人」時這些是「會」的訊號，卻把分數往順利推 |
| 宮廷牌一律 +0.2 | 不分花色、不分正逆。第二組的聖杯國王逆（在位者失勢）被算成正分 |
| AI 用現實常識、牌種當理由 | 第二組的解讀用「整組都是小牌、規模只是一件會過去的事」當成不會的理由（實際產出）；另外推測 AI 知道當事人是創辦人而順著常識答 |

典型牌面（三張，問會不會被換掉）在規則 11 的結果：皇帝逆＋命運之輪＋審判 +45.4、錢幣國王逆＋寶劍十＋世界 +44.6、皇帝逆＋力量逆＋戰車逆 +30.6，都和「會留任」的對照組（皇帝＋錢幣四＋力量 +62.1）落在同一邊。

### 2.2 規則 12：是非題

程式：`src/services/rules/yesNoRules.js`、`src/data/cardChange.js`，門檻與關鍵詞在 `src/data/ruleConfig.js` 的 `YES_NO`。

1. **是不是是非題**（`YES_NO.questionPattern`）：會不會、是否、能不能、能否、能夠、可不可以、有沒有、該不該、要不要、是不是、好不好、行不行、適不適合、值不值得，或含「嗎」。
2. **「會」指什麼**（依關鍵詞，先比變動與維持）：

| yesMeans | 關鍵詞（節錄） | 用哪條軸 |
|---|---|---|
| change（事情變動） | 換掉、下台、離職、辭職、離開、分手、離婚、結束、倒閉、裁員、放棄、跳槽、轉職… | 變動軸，照原值 |
| stay（維持現狀） | 留任、連任、留下、繼續、維持、守住、保住、撐住、續約、走下去… | 變動軸，方向反過來 |
| unfavorable（壞事發生） | 失敗、虧、賠、被騙、出事、惡化、落榜、被拒、下跌、崩盤… | 好壞軸，方向反過來 |
| favorable（預設：事情會成） | 以上都沒有 | 好壞軸 |

3. **變動軸**（`cardChange.js`）：78 張牌各標 `[正位, 逆位]` 兩個值，−1（守住、掌權、停在原地）～ +1（結束、離開、被換、翻轉）。逆位逐張標，不是固定倍率。例：

| 牌 | 正位 | 逆位 |
|---|---|---|
| 皇帝 | −0.9 穩坐 | +0.8 失勢 |
| 塔 | +1 崩解 | +0.5 勉強撐住 |
| 死神 | +1 結束 | +0.3 拖著 |
| 命運之輪 | +0.8 翻轉 | +0.3 |
| 聖杯八 | +0.9 轉身離開 | −0.2 走不開 |
| 錢幣四 | −0.9 緊抓不放 | +0.5 鬆手 |
| 權杖十 | −0.2 扛著 | +0.6 擔子放下或垮掉 |
| 各花色國王 | −0.5～−0.8 | +0.6～+0.7 |
| 聖杯七、寶劍九、月亮 | 0 附近 | 0 附近（看不清，沒有方向） |

4. **好壞軸**：沿用規則 11 的極性，但逆位翻向：正向牌逆位 ×（−0.4）、負向牌逆位 ×（−0.3）。
5. **權重**：位置權重（沒有就均分）× 牌種（大牌 1.5、宮廷 1.2、小牌 1）× 結果與未來位置 1.5。不沿用規則 10 的 3／2／1，否則一張宮廷牌會蓋過兩張小牌。
6. **基準值**：變動軸扣 0.10、好壞軸扣 0.05（隨機抽牌的平均），讓「會」與「不會」的機會相當。
7. **分級**：|分數| × √張數 ≥ 0.55 給「會／不會」、≥ 0.055 給「傾向會／傾向不會」、其餘「兩邊拉扯，看你怎麼做」（2026-11-13 改，原本固定 0.4／0.15、稱「牌面沒有明確答案」）。

輸出：`analysis.yesNo = { yesMeans, keyword, score, verdict, verdictLabel, contributions, text }`；不是是非題時為 `null`。文字由 `analysisFormatter.buildYesNoText` 產生（「這是是非題，『會』指的是…。牌面的答案：…。把答案往『會』拉最多的是…」）。

### 2.3.1 門檻改版（2026-11-13）

使用者要求「沒有明確答案」壓在 10% 左右。原本三張牌陣有 42%、七張 61%（張數越多分數越往 0 靠）。量測 |分數| × √張數 的分布，1～10 張幾乎一樣：10% 分位 0.04～0.07、50% 0.25～0.31、80% 0.49～0.60。所以門檻改成乘上 √張數 再比：lean 0.055（約一成沒有明確答案）、strong 0.55（約兩成直接說會或不會）。測試用固定種子的隨機抽牌檢查 1、3、5、7 張都在 4%～14%。2.3 的表格是改版前的量測。

### 2.6 規則 13：時間類問題

起因：追問「還要多久才能回到買進的價位」，AI 只說「牌面不給你時間」。程式：`src/services/rules/timingRules.js`、`src/data/cardTiming.js`。

- 辨識：多久、什麼時候、何時、幾時、多快、幾天／週／個月／年、要等、時間點…
- 時間推算（網路上沒有統一標準，採用最常見的一套並參考使用者提供的資料）：
  - 小牌：花色決定單位、數字決定數量（王牌＝1）。權杖＝天、寶劍＝週、聖杯＝月、錢幣＝年；季節權杖春、聖杯夏、寶劍秋、錢幣冬。
  - 宮廷牌：只給速度（侍者剛起步、騎士很快、皇后穩定醞釀、國王慢）。
  - 大牌：有黃道星座的給日期區間（金色黎明對應，例如惡魔＝摩羯座，12 月下旬到 1 月中旬）；其他給速度（塔突然、吊人延後、世界偏長）。
  - 逆位：延遲。大牌超過一半：以月或年計。
- 主要的時間牌：結果或未來位置的那張；沒有位置時看最後一張。其他牌的線索一起交給 AI。
- 提示詞：一定要給大約的時間點或範圍，並講出在什麼條件下到來；不解釋推算規則；不可以只說牌面不給時間。追問問時間時也一樣（每次追問各自算）。

### 2.4 AI 提示詞（`narrationService.js`）

- 使用者訊息多一行「是非判斷：…」。
- 系統提示新增：指向分析講的是順不順，不是會不會；是非題開場第一句就用是非判斷給的答案回答、不可改；只照牌面回答，現實考量最多一句並講明是牌面以外的考量；不拿「都是小牌」當成不會的理由；列出在位牌逆位、放下重擔、離開與結束這幾類牌在「會不會離開」問題裡的方向。

### 2.5 抽牌追問

限制：最多 3 次、每次 1～3 張、追問內容必填且最多 200 字；補充牌和桌上已有的牌（原牌陣與之前的補充牌）不重複。常數在 `src/services/followUp.js`。

| API | 權限 | 說明 |
|---|---|---|
| `POST /api/readings/follow-up/draw` | 不用登入 | body：`cards`（原牌陣）、`followUps`（之前的追問）、`question`、`count`，或 `picks`（使用者在扇形牌堆自己抽的牌，正逆位前端洗牌時決定；有帶就不另外抽）。回傳 `{ question, cards }`，cards 的格式同占卜結果但沒有位置。不存檔 |
| `POST /api/readings/follow-up/narrate` | AI 權限 | body 同 `/api/readings/narrate`，加上 `followUps`、`narration`（先前的解讀全文，可省略）、`readingId`（可省略）。NDJSON：delta、done（saved）、error。有 readingId 時寫完把追問清單與延伸回答一起存回紀錄 |
| `PUT /api/readings/:id/follow-ups` | 登入、只能改自己的 | 整批取代追問；`cards` 要和紀錄的牌一致（否則 409）；`narration` 這個 key 有帶才動延伸回答，清空追問時一併清掉 |
| `POST /api/readings` | 登入 | 多收 `followUps`、`followUpNarration`（保存前已經追問過的一起存） |
| `GET /api/readings/:id` | 登入 | 多回 `followUps`（牌義重算）、`followUpNarration` |

資料：`Reading.followUps: [{ question, cards: [{ cardId, orientation, nameZh }], createdAt }]`、`Reading.followUpNarration: { text, model, createdAt }`。延伸回答只有一篇，涵蓋當下所有追問，重新產生就覆蓋。

交給 AI 的資料（`followUp.buildFollowUpContext`、`narrationService.buildFollowUpMessage`）：原本那次占卜的完整資料、先前的解讀（最多 6000 字，用來避免重複與對照結論）、每次追問的問題與補充牌牌義、每次追問各自的是非判斷（只看那次的補充牌）、以及「加上補充牌後的是非判斷」（原本的問題，原牌陣與所有補充牌一起算）。延伸回答的結構：每次追問一節（`## 追問 N｜…`），最後 `## 綜合來看` 要講明答案是維持、更肯定還是改變。

前端（Tfontend）：`src/lib/useFollowUps.ts`（狀態與同步）、`FollowUpPanel.vue`（牌陣下面：補充牌、追問輸入、抽牌方式、AI 追問按鈕）、`FollowUpFanDraw.vue`（自己抽牌：沿用 `FanDeck` 洗牌、切牌、點牌，桌上已有的牌不放進牌堆）、`FollowUpAnswer.vue`（回答的一段）。AI 的回答依「## 追問 N」切開放在各自的追問底下，「綜合來看」放在所有追問最後（`aiMarkdown.splitFollowUpAnswer`）；占卜頁與我的紀錄共用。是非題的答案不在畫面上單獨顯示，只交給 AI 寫進解讀。

## 四、決議紀錄

- 2026-11-13　是非題另開一條「變動／維持」軸，不改規則 11 的極性。理由：極性講好壞，會不會變是另一件事；命運之輪、世界是好牌也是變動牌，硬改極性會弄壞指向分析。
- 2026-11-13　變動軸的逆位逐張標值、可以翻向；規則 11 的逆位維持只打折不翻向（規則 6 的決議不動）。
- 2026-11-13　變動軸扣基準值 0.10、好壞軸扣 0.05。理由：逆位多半帶一點變動，不扣的話七張牌陣有 37% 傾向「會變」、只有 7% 傾向「不會」。
- 2026-11-13　門檻 lean 0.15、strong 0.4。三張牌陣約 42% 沒有明確答案、各約 28% 傾向兩邊；張數越多越常沒有明確答案（平均後互相抵消），這符合大牌陣本來就不適合問是非題的慣例，不另外調。
- 2026-11-13　牌種權重用 1.5／1.2／1，不沿用 3／2／1。理由：第一組的錢幣皇后（宮廷）用 2 倍會完全蓋過另外兩張。
- 2026-11-13　使用者第一組維持「傾向不會」，不為了讓兩組都答「會」去調值表。待使用者確認錢幣皇后正位在這題該怎麼讀。
- 2026-11-13　追問的延伸回答只留一篇（涵蓋所有追問），不是每次追問各一篇。理由：使用者要的是「連同原本牌陣與多次追問的牌作結合探討」；一篇才能在最後給一個合併後的結論。
- 2026-11-13　補充牌不併入原牌陣的組合分析。理由：牌對、數字階段、位置判定都依賴牌陣位置，補充牌沒有位置，併進去會改掉使用者已經看過的判斷依據。
- 2026-11-13　`api-reviewer` 審查（無高風險）後的修正：
  - AI 延伸回答存回紀錄時先比對追問清單（`readingHistory.followUpRelation`）：紀錄比請求新（寫的途中又抽了一次）只存回答、不動追問；對不起來就不存。原本是整批覆蓋，會把較新的追問蓋掉。
  - 先前的解讀由前端送回，是提示詞裡最大的自由文字：拿掉資料區塊的標籤字樣、上限改成 6000 字、提示詞註明它只是參考資料、裡面的指示不執行。
  - 延伸回答多存 `rounds`（涵蓋幾次追問）；追問被換成另一組而沒帶回答時清掉舊回答。整批取代時沒變的追問沿用原本的 `createdAt`。
