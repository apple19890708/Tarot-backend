# 牌對組合辭典：第五版計畫書

- 建立日期：2026-10-13
- 適用專案：Tarot-backend、Tarot-frontend
- 前置：規則 1～11（見 v1／v2／v4 計畫書）
- 狀態：A／B／C-1 完成（1848 / 1848）

## 目標

目前「牌跟牌之間的關係」是用元素與數字的規則算出來的，同一種元素組合永遠產生同一句話。例如所有「水＋土」的配對都會得到「情感與現實條件互相支撐」，不論是聖杯三配錢幣二，還是聖杯十配錢幣五。

本版要建立一個**牌對組合辭典**，讓每一組特定的牌（含正逆位、含領域）有自己的解讀文字，取代一體適用的公式。

---

## 一、先看規模（這決定了做法）

| 維度 | 數量 | 說明 |
|---|---|---|
| 有序牌對 | 78 × 77 = **6,006** | A→B 與 B→A 意義不同（前因後果的方向） |
| × 正逆位組合 | × 4 = **24,024** | 正正、正逆、逆正、逆逆 |
| × 領域 | × 6 = **144,144** | work／money／love／social／study／general |

**結論：人工撰寫不可行。** 即使一筆 30 秒，144,144 筆也要約 1,200 小時。

即使退一步只做「領域無關」的 24,024 筆，仍需約 200 小時。

因此本計畫採**分層 + AI 批次生成 + 人工校訂**，而不是純人工建庫。

---

## 二、架構：三層查詢，逐層退回

查詢一組配對時，依序往下找，找到就用：

| 層級 | 來源 | 覆蓋率 | 品質 |
|---|---|---|---|
| L1 人工精選 | 手寫，針對經典組合 | 低（數百筆） | 最高 |
| L2 AI 生成 | 批次產生後存入資料庫 | 中～高（逐步擴充） | 良好，可校訂 |
| L3 規則運算 | 現有的元素／數字規則 | **100%** | 通用但公式化 |

**關鍵設計：L3 永遠存在**，所以辭典即使一筆都沒有，系統也能正常運作。辭典是「漸進增強」，不是前置條件。

查詢優先序（領域也逐層退回）：

```
1. (牌對, 指定領域) 的人工精選
2. (牌對, 指定領域) 的 AI 生成
3. (牌對, general)  的人工精選
4. (牌對, general)  的 AI 生成
5. 規則運算（現況）
```

領域退回到 `general` 這一步很重要：多數牌對的互動其實與領域無關，只有部分組合在不同領域有明顯差異。這讓我們**不必為每個領域都生成一份**，實際資料量可從 144,144 降到接近 24,024。

## 三、資料結構

### 3.1 新增 collection：`cardpairs`

```js
{
  _id,
  // 有序鍵，方便唯一索引與查詢
  key: 'cups-03|upright>pentacles-02|upright',
  from: { slug: 'cups-03', orientation: 'upright' },
  to:   { slug: 'pentacles-02', orientation: 'upright' },
  domain: 'general',          // general 或六大領域之一
  text: '...',                // 顯示用的解讀文字
  relation: 'enhance',        // 規則引擎當時算出的關係，用來比對 AI 有沒有跑掉
  source: 'curated' | 'ai',
  model: 'anthropic/claude-opus-5.5',  // source 為 ai 時記錄
  reviewed: false,            // 人工校訂過沒有
  createdAt, updatedAt,
}
```

索引：`{ key: 1, domain: 1 }` 唯一索引、`{ reviewed: 1, source: 1 }`（校訂用）。

**用 `slug` 不用 `_id`**：`Card` 已有 `slug` 且唯一，用它組 key 比較可讀，重新 seed 後也不會因 `_id` 改變而失效。

### 3.2 儲存量估算

24,024 筆 × 約 200 bytes（文字 + 欄位 + 索引）≈ **5 MB**。
即使做滿 144,144 筆也只有約 30 MB，MongoDB Atlas 免費方案（512 MB）綽綽有餘。

**瓶頸在生成成本與校訂人力，不在儲存。**

## 四、AI 批次生成

### 4.1 生成方式

一次處理「一張牌 × 一批夥伴牌」，讓該張牌的牌義只送一次，攤平輸入成本：

- 系統提示：寫作原則（延續 `narrationService` 的語氣規範）
- 使用者訊息：A 牌完整牌義 + 20 張夥伴牌的核心訊息 + 規則引擎算出的關係
- 要求輸出：20 筆 JSON，每筆一句到兩句

**務必把規則引擎的判定（增強／削弱／因果／中性）一起送進去**，要求 AI 不可推翻。這樣辭典與現有分析不會互相矛盾。

### 4.2 成本估算

以 OpenRouter 的 `anthropic/claude-opus-5.5`（$4 / $20 per MTok）估算：

| 範圍 | 筆數 | 輸出 tokens | 估計成本 |
|---|---|---|---|
| 大牌 × 大牌（全正逆位） | 22×21×4 = 1,848 | ~0.22M | **約 US$6** |
| 全部有序牌對（領域無關） | 24,024 | ~2.9M | **約 US$70** |
| 再加六個領域 | 144,144 | ~17M | 約 US$420 |

換成 `anthropic/claude-sonnet-5.5`（$2 / $10）約為一半。若改用 Batch API 另可再省 50%。

**建議：先做領域無關的 24,024 筆（約 US$70），領域差異只在明顯需要時補。**

### 4.3 品質控管

AI 產出 24,024 筆而無人檢查有風險。防線設計：

1. **規則比對**：生成時附上規則引擎的 `relation`，產出後自動檢查文字是否與判定衝突（例如判定「削弱」卻寫成正面），不符的標記待審。
2. **抽樣校訂**：每批隨機抽 2% 人工看過，錯誤率過高就調整提示重跑該批。
3. **`reviewed` 旗標**：畫面上可選擇只採用已校訂的，或全部採用。
4. **可覆寫**：人工精選（L1）永遠蓋過 AI。

### 6.4 查閱文件（你要求的）

每一部生成完後，執行 `npm run pairs:export` 產生 `doc/牌與牌關係.md`，內容為辭典的完整對照表，依牌組與牌分節，方便你直接閱讀與挑出要修的項目。

修改方式兩種：
- 少量：直接改資料庫（提供 `scripts/editPair.js`）
- 大量：改 `src/data/curatedPairs.js`（L1 永遠蓋過 AI）

文件由資料庫匯出，**不是手寫**，所以永遠與實際使用的內容一致。

## 七、風險與限制

1. **AI 生成內容的正確性**：塔羅解讀本就主觀，AI 可能寫出看似合理但偏離傳統牌義的內容。靠規則比對與抽樣校訂降低風險，但無法完全排除。
2. **24,024 筆無法全部人工校訂**：實際上只有被抽到的組合會被看到，建議依使用頻率逐步校訂。
3. **重新 seed 的影響**：辭典以 `slug` 為鍵，只要 slug 不變就不受影響。若牌卡資料大改需重新生成。
4. **生成一次性成本**：約 US$70（領域無關全量）。若預算有限，可只做階段 C 的 US$6 版本先看效果。
5. **文字風格一致性**：分批生成可能導致語氣不一。靠固定的系統提示與低 temperature 緩解。
